### CU-04 · Cambiar modo operacional

| **Módulo · Prioridad** | M02 · Control de Modos Operacionales · Prioridad Crítica · Etapa 3 |
| --- | --- |
| **Actor primario** | Administrador |
| **Actores secundarios** | — |
| **Requisitos** | RF-01, RF-02, RF-03, RF-04, RN-01, RN-02, RN-07, RNF-06, RNF-07 |
| **Descripción** | Permite a un Administrador autorizado conmutar la plataforma entre Modo Cotidiano y Modo Emergencia (y volver), registrando el motivo y el estado anterior y nuevo. Las aplicaciones adaptan menús y flujos sin reinstalarse. |
| **Precondiciones** | El administrador tiene sesión vigente y permiso para activar o desactivar el Modo Emergencia (RN-01). Existe un modo operacional vigente. |
| **Disparador** | El administrador usa el interruptor «Modo cotidiano / Modo emergencia» del dashboard. |
| **Flujo principal** | **1.** El sistema muestra el modo vigente y la opción de cambiarlo.  **2.** El administrador selecciona el modo al que desea pasar.  **3.** Al activar la emergencia, el administrador indica el tipo de evento (sismo, inundación o deslizamiento), el motivo y las zonas o poblaciones a notificar.  **4.** El sistema pide confirmación explícita del cambio.  **5.** El sistema ejecuta CU-03 para validar la autenticación reforzada.  **6.** El sistema verifica que el usuario esté autorizado para el cambio.  **7.** El sistema actualiza el estado operacional global, conservando el historial anterior.  **8.** El sistema registra en auditoría (CU-05): usuario, fecha y hora, motivo, estado anterior y nuevo.  **9.** El sistema publica el nuevo estado; las aplicaciones lo consultan y reconfiguran menús, accesos y banners.  **10.** Si se activó la emergencia, el sistema dispara las notificaciones de crisis (CU-06) y suspende el cobro de comisiones y planes.  **11.** El sistema confirma el cambio al administrador. |
| **Flujos alternativos** | **A1** Desactivación: el administrador indica el motivo de cierre; la plataforma vuelve al Modo Cotidiano y conserva todo el historial (RN-02).  **A2** El administrador cancela en la confirmación: no se modifica el estado.  **A3** Un cliente está sin conexión en el momento del cambio: adopta el estado vigente al reconectarse y consultar (RF-02). |
| **Excepciones** | **E1** Usuario sin autorización: el sistema niega el cambio y registra el intento (CU-05).  **E2** Falla la autenticación reforzada (CU-03): el cambio no se aplica.  **E3** No se puede persistir el cambio o su registro de auditoría: el estado no cambia (operación atómica) y se informa el error.  **E4** El modo seleccionado ya está vigente: el sistema lo informa sin cambios. |
| **Postcondiciones** | El modo operacional global queda actualizado y consultable por todos los clientes. El historial de activaciones y desactivaciones se conserva. Con la emergencia activa, se habilitan los módulos M09 a M13. |
| **Reglas de negocio** | RN-01: solo un usuario autorizado activa o desactiva el Modo Emergencia. RN-02: todo cambio conserva trazabilidad y no elimina el historial. En la v1.0 el modo es global; solo las notificaciones se segmentan por zona. No existe activación automática por sensores o fuentes externas (fuera del alcance). |
| **Relaciones** | «include» CU-03 (MFA). «include» CU-05 (auditoría). «extend» de CU-06 (emite notificaciones al activar la emergencia). |
| **Criterios de aceptación** | Un administrador autorizado cambia el modo; los clientes reciben el nuevo estado y muestran únicamente las funciones permitidas. El cambio queda en la auditoría con usuario, fecha y hora, motivo y estados anterior y nuevo. |
